# Advanced Site Analyzer — План доработки бэкенда (для Claude Code)

> Рабочий план для исполнения через Claude Code. Цель — довести существующий
> бэкенд до продакшен-качества. **Вне scope этого плана:** сборка .exe/установщик,
> редизайн GUI, подписки, лицензирование, монетизация. Занимаемся только
> практической/бэкенд-частью.

---

## 0. Обязательные правила (house rules — соблюдать в каждой задаче)

Проект уже следует строгой архитектуре. Claude Code ДОЛЖЕН её сохранять:

- **Слоение:** чистый offline-контракт → стор → runner → тонкие surfaces (GUI/web/CLI).
  Новую логику класть в чистый модуль, а GUI/web делать тонкими вызовами.
- **Без второго стора.** Использовать существующие `FindingsStore`/`AssetStore`/
  `MissionStore` и т.д. Никаких дублирующих источников истины.
- **Derive-on-read** для отчётов/overview/timeline — вычислять из сохранённых
  данных, не писать в стор при чтении.
- **После КАЖДОЙ задачи:** `ruff check .` чистый; полный `pytest` зелёный;
  GUI `python main.py --self-check` проходит и печатает корректное число вкладок.
- **Коммиты атомарные**, по одной подзадаче; в сообщении — что и зачем.
- **Никакого копирования чужого кода.** Любые «нативные реализации» (WS5) пишутся
  как оригинальный код по описанию поведения, не транслируются из чужих исходников.
- **safe-by-default** сохраняется: новые сетевые действия — только за галочкой и
  через существующий Scope Guard.

Порядок исполнения workstream'ов: **WS1 → WS2 → WS6(частично) → WS3 → WS4 → WS5**.
Обоснование: сначала убрать лишнее (WS1), поставить страховку от падений (WS2),
закрыть быстрые дыры надёжности, затем крупные инвестиции (async, алертинг),
и в конце — долгий трек нативных реализаций.

## WS2 — Crash-репортер и наблюдаемость

**Цель.** Ловить все классы падений (главный поток, воркеры, hard-crash Qt/C++,
Qt-сообщения), сохранять структурированный отчёт локально, показывать его на
следующем старте, давать opt-in отправку. **Local-first** (не ломать
offline/privacy-позиционирование — никакой авто-отправки в облако).

**Новый модуль `core/crash_reporter.py`:**
- `install()` — ставит `sys.excepthook`, `threading.excepthook`,
  `faulthandler.enable(file=...)` (segfault-трейс в отдельный файл),
  Qt-хендлер через `qInstallMessageHandler` (перехват qWarning/qCritical/qFatal).
- `breadcrumb(msg)` — кольцевой буфер (`deque(maxlen=50)`) последних действий.
- `_redact(text)` — вырезать токены/api-key/authorization/cookie и сканируемые URL
  перед сохранением/показом.
- `_write_report(kind, detail)` — JSON: time, app_version, os, python, qt,
  traceback (редактированный), breadcrumbs. Писать в
  `PathManager.data_dir / "crashes"`.
- `pending_crashes()` — вернуть несёнтенные отчёты для показа на старте.

**Интеграция:**
- В `main.py` вызвать `crash_reporter.install()` ДО `QApplication(...)`.
- Единый источник версии приложения (константа/файл), использовать в отчёте.
- В воркерах (`gui/workers.py`, `gui/task_runner.py`) обернуть `run()` так, чтобы
  исключение фонового потока попадало в репортер, а не терялось.
- `breadcrumb(...)` расставить на ключевых действиях GUI (открыт проект, старт
  Full Collection/скана, смена вкладки/режима).
- Диалог на старте (`pending_crashes()` не пуст): «Прошлый сеанс завершился
  аварийно» + [Посмотреть] [Отправить] [Пропустить]. Отправка = HTTPS POST на
  настраиваемый endpoint ИЛИ «скопировать отчёт»; по умолчанию ничего не
  отправляется.

**Тесты (`tests/test_crash_reporter.py`):** редактирование секретов работает;
отчёт пишется валидным JSON со всеми полями; breadcrumbs обрезаются до maxlen;
`pending_crashes()` находит/не находит корректно; excepthook пишет отчёт и не
глотает (пробрасывает в `sys.__excepthook__`).

**Критерии приёмки.** Искусственное исключение в главном потоке и в воркере
создаёт по отчёту; faulthandler-файл появляется; в отчёте нет сырых
токенов/cookie; ruff/pytest/self-check зелёные.

## WS3 — Async-движок конкурентного сканирования

**Цель.** Главная конкурентная инвестиция. Сейчас прогон скорее
последовательный. Сделать конкурентное выполнение независимых фаз/целей с
ограничением параллелизма — это то, что ставит инструмент в один ряд с топовыми
по скорости на крупных целях.

**Подход (эволюция, не переписывание с нуля):**
- Ввести чистый «планировщик задач» `core/scan_engine.py`: описывает фазы как
  узлы с зависимостями (DAG), запускает независимые параллельно, зависимые — по
  готовности предков. Ограничение конкурентности (`max_concurrency` из настроек).
- Транспорт: `asyncio` + пул для блокирующих вызовов (`run_in_executor`) для
  синхронных сетевых функций, ЛИБО `concurrent.futures.ThreadPoolExecutor` если
  так проще интегрировать с существующим синхронным кодом. Выбрать один подход,
  не смешивать хаотично.
- Переиспользовать общий HTTP-слой с ретраями (`utils/http_retry.py`), добавить
  ограничение rate-limit на хост, чтобы не долбить цель.
- `core/collection_runner.py` и `core/recon_engine.py` перевести на движок:
  фазы, которые не зависят друг от друга (subdomains / tech-fingerprint / cookie
  / headers и т.п.), должны идти параллельно; отмена (cancel) должна корректно
  прерывать все ветки.
- Сохранить существующий контракт логов/прогресса (`self._log(...)`) и warning-
  учёт по best-effort этапам — вывод для пользователя не должен «поехать».

**Тесты:** DAG исполняется в правильном порядке; независимые узлы реально
конкурентны (проверка через тайминги/фейковые задержки, как в существующем
`test_zero_delay_skips_sleep`); отмена прерывает все ветки; rate-limit на хост
соблюдается; результат прогона идентичен последовательному (те же
findings/assets).

**Критерии приёмки.** Full Collection на многофазной цели заметно быстрее при
том же наборе результатов; отмена мгновенна; ruff/pytest/self-check зелёные.

## WS4 — Алертинг поверх мониторинга (дожать, не строить с нуля)

**Цель.** Сделать инструмент «липким»: при diff'е на непрерывном мониторинге
(новый субдомен, новый CVE/KEV, ослабленный DMARC, новый attack-path) —
уведомление в канал. Каналы Discord/Telegram/email **уже есть** в
`core/alerts.py` (через `urllib`/`smtplib`, без новых зависимостей).

**Что сделать:**
- Добавить **Slack** как канал (входящий webhook — по форме идентичен Discord;
  минимальная работа в `core/alerts.py`, метод транспорта переиспользуется).
- Обобщённый **generic webhook** (произвольный URL, JSON-payload) для интеграций
  пользователя (SIEM/自own endpoint).
- Убедиться, что `core/monitor.py` (tick/watch) реально дёргает `alerts` на
  событиях из `core/scan_diff.py`: проверить, что каждый значимый тип diff'а
  (`new_subdomain`, `new_cve`, `dns_email_auth_weakened`, `new_attack_path` и др.)
  доходит до канала. Где обрыв — соединить (на уровне драйвера/`extra_tick`,
  движок мониторинга оставить развязанным, как у Mission Center M10).
- Конфиг каналов — в settings.json; секреты webhook'ов НЕ логировать (учесть
  редактирование, как в WS2).
- Дедуп/anti-spam: не слать одно и то же событие повторно (ключ события +
  «уже уведомлено»), чтобы мониторинг не заваливал канал.

**Surfaces:** тонкая настройка каналов в System-вкладке; web — эндпоинт тест-
отправки («send test alert»); CLI (`monitor_cli`) — уже есть, проверить вывод.

**Тесты:** Slack/generic webhook формируют корректный payload (мок транспорта);
diff→alert проходит для каждого типа события; дедуп не шлёт дубликаты; секреты
не попадают в логи.

**Критерии приёмки.** На тестовом diff'е приходит одно уведомление в
настроенный канал, повтор не приходит; ruff/pytest/self-check зелёные.

## WS5 — Нативные реализации функций внешних инструментов (снять зависимость от бинарников)

**Цель.** Убрать необходимость пользователю ставить внешние бинарники, реализовав
нужную узкую функциональность **собственным оригинальным кодом**. Продукт должен
работать «из коробки» на базовом уровне, а внешние инструменты — оставаться
опциональным усилением через существующий subprocess-адаптер.

**Правило для Claude Code:** писать реализации ПО ОПИСАНИЮ ПОВЕДЕНИЯ, не заглядывая
в чужие исходники и не транслируя их. Алгоритм не защищён — конкретный код чужой
защищён. Код должен быть оригинальным и принадлежать проекту.

**Кандидаты (по приоритету пользы):**
1. **Пассивное перечисление субдоменов** — расширить существующие нативные
   источники (`core/subdomain_scanner.py`: crt.sh, HackerTarget, AlienVault OTX,
   Anubis) новыми пассивными API, чтобы во многих сценариях не требовался внешний
   `subfinder`/`amass`. Внешние оставить опциональным источником.
2. **Сканер секретов** — у тебя уже есть нативный `core/secret_scanner.py` +
   `secret_validator.py`. Проверить покрытие паттернов (vendor-форматы, JWT,
   Basic), чтобы внешний `SecretFinder` (GPL) стал необязательным. Никакого его
   кода — только свои паттерны/логика.
3. **Краулер эндпоинтов** — лёгкий нативный обход (уже частично есть через
   `content_capture`/`site_map`/`scrapy_crawler`), чтобы `katana` был опцией, а не
   требованием для базового прогона.

**Что НЕ реализовывать нативно:** тяжёлый vuln-скан (nuclei с его шаблонной базой)
— оставить как опциональный внешний инструмент через adapter; воспроизводить
шаблонную экосистему нецелесообразно.

**Тесты:** каждый нативный источник/сканер — на моках сетевых ответов;
деградация «внешний инструмент отсутствует → нативный путь работает»;
результаты нативного и внешнего пути совместимы по формату (одинаковые
Finding/Asset DTO).

**Критерии приёмки.** Базовый Full Collection даёт осмысленный результат БЕЗ
единого установленного внешнего бинарника; при наличии внешних — они усиливают,
но не требуются; ruff/pytest/self-check зелёные.

## WS6 — Надёжность иハーдening (полировка существующего)

**Цель.** 31 вкладка и 52k строк ценнее, если каждая работает на 100%. Этот трек
идёт частично параллельно (быстрые пункты — сразу после WS2).

**Пункты:**
- **Web-консоль:** добавить **rate-limiting** на мутирующие эндпоинты (запуск
  сканов/tool-run/mission-run) — сейчас его нет. Реализовать простой лимитер на
  stdlib (окно/токен-бакет per-token/per-IP), без тяжёлых зависимостей. Также
  явно задокументировать в коде, что LAN-режим без TLS небезопасен вне
  доверенной сети (у тебя уже есть token + bind 127.0.0.1 по умолчанию — это
  хорошо, дожать rate-limit и CSRF на POST).
- **Аудит `except Exception`** (~192 штук в core): пройтись, где «глотается»
  ошибка без лога — добавить логирование/breadcrumb (связка с WS2), чтобы
  проблемы были видимы, а не тихо терялись. Не менять поведение best-effort фаз,
  только сделать сбои наблюдаемыми.
- **Единый источник версии** приложения (используется в WS2 и в отчётах).
- **Пользовательские сообщения об ошибках** вместо сырых traceback в GUI-диалогах
  (traceback — в crash-репорт, пользователю — понятный текст).
- **Механизм проверки обновлений** (лёгкий: запрос версии с настраиваемого
  endpoint, уведомление «доступна новая версия»; без авто-апдейта). Opt-in.

**Критерии приёмки.** Перебор запросов к web-консоли отбивается лимитером;
проглоченные исключения теперь логируются; в GUI при сбое — понятное сообщение +
запись в crash-репорт; ruff/pytest/self-check зелёные.

## Порядок и Definition of Done по всему плану

**Последовательность:** WS1 → WS2 → быстрые пункты WS6 → WS3 → WS4 → WS5 →
остаток WS6.

**Общий Definition of Done (проверять на каждом шаге):**
1. `ruff check .` — All checks passed.
2. Полный `pytest -q` — зелёный (единственный допустимый warning — известный
   Starlette/httpx deprecation).
3. `python main.py --self-check` — OK, число вкладок соответствует ожидаемому
   (после WS1 — на 1 меньше).
4. Обновлён `PROJECT_STATUS.txt` кратким блоком по завершённому WS (в стиле
   существующих записей: что сделано, файлы, рост числа тестов).
5. Атомарные локальные коммиты, без push (как принято в проекте).

**Что осознанно вне scope (по решению владельца):** сборка .exe / установщик,
редизайн интерфейса, подписки, лицензирование, монетизация. Не трогать.
